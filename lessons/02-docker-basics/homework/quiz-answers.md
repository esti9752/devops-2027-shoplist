אסתי נדל>

1.ג. דרך עבודה: אחריות משותפת על הקוד מהכתיבה ועד שהוא רץ אצל המשתמשים
2.ב. Release
3.ב. כל האפליקציה עלולה ליפול, כי זה תהליך אחד
4.* באמצעות פרוטוקולים רשתיים כמו HTTP/REST API, gRPC, או דרך מתווך הודעות (Message Broker) כמו RabbitMQ או Redis.
5.א. ל-backend
6.* כי סרוויס ה-stats אינו ניגש ישירות למסד הנתונים, אלא מקבל את הנתונים המעובדים (או מתקשר דרך ה-backend).
7.* מורכבות ניהולית ותפעולית גבוהה
* **Image** הוא תבנית סטטית (Blueprint) המכילה את קוד המקור וההגדרות, ואילו **Container** הוא המופע (Instance) הרץ והפעיל של אותו Image בזמן אמת.
9.ב. נשאר
10.ב. containers משתפים את ה-kernel של המחשב, ולכן הם קלים ועולים בשניות
11.* זהו הפורט במחשב המארח (Host) דרכו לגשת לקונטיינר מבחוץ.
12.ב. מתעד שהאפליקציה מאזינה בפורט 5000, ולא פותח כלום
13.* כדי לנצל את מנגנון ה-Cache של Docker. מכיוון שקוד המקור משתנה בתדירות גבוהה יותר מקובץ התלויות, הפרדת השלבים מונעת את הרצה מחדש של התקנת החבילות בכל שינוי קטן בקוד.
14.* כי `localhost` בתוך הקונטיינר מפנה אך ורק פנימה אל עצמו, ואילו `0.0.0.0` מאזין לכל ממשקי הרשת ומאפשר לקבל בקשות חיצוניות מהמארח (Host).
15.* מטעמי אבטחת מידע (מניעת חשיפת נתונים רגישים בקוד המקור) וגמישות תפעולית בין סביבות שונות.
16.* נתיב ה-`/health` בודק רק אם השרת עצמו חי, בעוד שנתיב ה-`/stats` נכשל כנראה עקב חוסר יכולת לתקשר עם רכיב חיצוני התלוי בו (כמו מסד נתונים או שירות אחר).
17.* `docker stop` עוצר את התהליך שרץ בתוך הקונטיינר, ואילו `docker rm` מוחק את הקונטיינר לחלוטין מהדיסק.
18.* Docker הוריד את התגית `latest`. זה לא מתאים לסרוויס אמיתי כי הגרסה עלולה להשתנות בהפתעה בעתיד ולפגוע بيציבות המערכת; בסביבת ייצור חובה להשתמש בגרסה ספציפית וקבועה.
